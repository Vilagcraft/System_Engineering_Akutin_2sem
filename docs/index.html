🎯 Миссия системы

Высоконадёжная (доступность ≥99.95% в месяц), безопасная, соответствующая 115-ФЗ, 259-ФЗ, ГОСТ Р 34.10-2021 платформа криптобиржи RocketSpot.

  • Self-service управление API-ключами (корпоративный клиент)
  • Оркестрация холодных/горячих кошельков с M-of-N мультиподписью
  • Централизованный аудит с логической изоляцией tenant-данных (namespace + RBAC)
  • Поддержка блокчейнов: BTC, ETH, TRON (расширяемо по критериям)

1. Контекст и границы системы (SoI)

1.1 Цель системы

Спроектировать, реализовать и эксплуатировать высоконадёжную (доступность ≥99.95% в месяц), безопасную и соответствующую нормативным требованиям платформу для криптовалютной биржи RocketSpot.

1.2 Контекст (Среда и внешние системы)

  • Эксплуатационная среда: Гибридное облако (Yandex Cloud) + on-premise ЦОД, изолированные сегменты сети (DMZ, сеть обработки платежей, HSM-сегмент)
  • Операционный контур: Platform Engineering, DevOps, SecOps, Treasury, Compliance, Legal
  • Ключевые ограничения: 115-ФЗ, 259-ФЗ, ФЗ-152, ГОСТ Р 34.10-2012/2021, обязательное использование HSM on-premise кластера

1.3 Внешние сущности и потоки данных

1.4 Границы SoI

Внутри SoI (разрабатываемые компоненты)

  • Торговый движок (Rust/C++)
  • API Gateway (Kong/Traefik)
  • Оркестратор кошельков (Go + Temporal)
  • HSM-Адаптер (PKCS#11)
  • AML Risk Engine (Python/FastAPI)
  • KMS (Key Management Service)
  • Аудиторское хранилище (WORM, retention 7 лет, 10k событий/сек)
  • Admin Back Office

Снаружи SoI (интегрируемые системы)

  • HSM Cluster (КриптоПро on-premise, 3 узла)
  • Блокчейн-ноды (BTC/ETH/TRON)
  • SIEM (MaxPatrol)
  • KYC сервис (Sumsub)
  • Платежные шлюзы (Сбер, Т-Банк)

Границы ответственности

RocketSpot отвечает за корректную оркестрацию заявок, соблюдение политик безопасности (M-of-N, AML), генерацию и подпись транзакций через HSM, а также за неизменяемый аудит. Внешние системы предоставляют сервисы по SLA.

1.5 Обоснование выбора интеграций

HSM Cluster: Требование 115-ФЗ и ГОСТ Р 34.10-2021. Аппаратная защита ключей, сертифицирована ФСБ. Развёртывание: on-premise кластер из 3 узлов, синхронная репликация, p99 latency <500 мс.

Блокчейн-ноды: Взаимодействие с публичными сетями. Scope ограничен тремя блокчейнами (BTC, ETH, TRON) с возможностью добавления по критериям.

SIEM (MaxPatrol): Требование ЦБ РФ к мониторингу инцидентов ИБ.

KYC сервис (Sumsub): Требование 115-ФЗ для идентификации клиентов.

Платежные шлюзы: Фиатные депозиты/выплаты в рублях для российских клиентов.

1.6 Допущения

  • SLA внешних интеграций ≥99.9%
  • HSM on-premise кластер с синхронной репликацией
  • Блокчейн-ноды синхронизированы, диск ≥2 ТБ
  • TLS 1.3 и VPN для платёжных шлюзов
  • 2FA для доступа к админке
  • Резервное копирование БД каждые 6 часов (RPO <6 ч)
  • Dual control для админ. действий
  • Целевая нагрузка: 50k concurrent, 10k RPS, p99 <200 мс

Сценарии использования (5)

S1: Вывод криптовалюты (основной сценарий)

Цель: Безопасный вывод средств

Шаги: Инициирование → Pre-flight (2FA, AML) → Блокировка средств → Сборка транзакции → Согласование (<10k авто, ≥10k step-up) → Подпись HSM → Публикация → Финализация

Исключения: Недостаточно средств, адрес в чёрном списке, превышен лимит

Деградация: HSM недоступен → pending_hsm, retry; AML недоступен → ручное рассмотрение

S2: Создание API-ключа для алгоритмической торговли

Цель: Self-service выдача ключей

Шаги: 2FA → Выбор scope → IP whitelist для withdraw → KYC → Генерация ключа → Сохранение хеша → Аудит

Исключения: Нет IP whitelist, дублирование имени, лимит ключей, KYC не пройден

Деградация: БД недоступна → 503; API Gateway недоступен → pending_gateway

S3: Мультиподпись для вывода из холодного хранилища

Цель: Безопасный вывод крупных сумм (>100k USD)

Шаги: Инициация казначеем А → Создание multisig-запроса → Уведомление казначеев Б и В (кворум 2 из 3) → Подтверждение в админке → HSM собирает подписи → Отправка → Аудит

Исключения: Недостаточно подписей за 24 часа, ошибка подписи, конфликт UTXO

Деградация: HSM недоступен → pending_hsm; подписант недоступен → эскалация

S4: Плановая ротация мастер-ключей HSM

Цель: Смена ключей без простоя, dual control

Шаги: SecOps-1 инициирует → SecOps-2 подтверждает → HSM генерирует новый ключ → Перешифровка кошельков → Валидация → Архивация старого ключа → Аудит

Исключения: Отказ подтверждения, ошибка перешифрования, HSM в maintenance

Деградация: Частичная перешифровка → повтор через 1 час; сбой архивации → локальное сохранение

S5: Расследование инцидента и формирование compliance-отчёта

Цель: Отчёт за 1 час по запросу аудитора

Шаги: Ввод correlation_id → Сбор из WORM → Формирование шкалы → Обогащение из SIEM → Экспорт PDF/CSV → Подпись ЭЦП

Исключения: Неполные данные → EvidenceGap; доступ запрещён → 403; период >1 года → 400

Деградация: SIEM недоступен → только локальное WORM; часть логов отсутствует → отметка

4.4 Архитектурные решения (ADR) с альтернативами

ADR-1: HSM для ключей

Контекст: Соответствие 115-ФЗ, ГОСТ

Решение: КриптоПро on-premise кластер

Альтернативы: Vault (не соответствует 115-ФЗ), Cloud HSM (нет сертификации)

Trade-off: +40% бюджета vs защищённость

ADR-2: Saga Pattern (Temporal)

Контекст: Длительные операции вывода

Решение: Temporal.io

Альтернативы: Camunda (тяжеловесная), ручная Kafka (сложно)

Trade-off: Сложность отладки vs гарантия финишности

ADR-3: Изоляция движка и кошельков

Контекст: Производительность vs безопасность

Решение: Физическое разделение, Kafka

Альтернативы: Монолит (риск lateral movement), синхронные REST (задержки)

Trade-off: +50 мс latency vs изоляция

ADR-4: PostgreSQL vs MongoDB

Контекст: ACID для финансов

Решение: PostgreSQL 15+

Альтернативы: MongoDB (слабая ACID), CockroachDB (избыточна)

Trade-off: Меньшая горизонтальная запись vs консистентность

ADR-5: Kafka vs RabbitMQ

Контекст: Высокая пропускная способность

Решение: Apache Kafka

Альтернативы: RabbitMQ (меньше пропускная), Kinesis (vendor lock-in)

Trade-off: Сложнее настройка vs replayability

ADR-6: Kubernetes vs Nomad

Контекст: Гибридное облако + on-premise

Решение: Kubernetes

Альтернативы: Nomad (проще, но меньше экосистема), Swarm (недостаточно)

Trade-off: Высокая сложность vs стандарт

5. Интерфейсы (ICD-lite)

POST /api/v2/withdraw

{
  "currency": "BTC",
  "address": "1A1zP1eP5QGefi2DMPTfTL5SLmv7DivfNa",
  "amount": "0.5",
  "network": "BTC",
  "twofa_code": "123456"
}

Idempotency-Key обязателен. Retry: экспоненциальная задержка 1с,2с,4с до 3 попыток.

Коды ответов:

  • 202 – принято
  • 400 – неверный формат
  • 401 – неверная подпись/2FA
  • 403 – недостаточно прав
  • 409 – дублирование Idempotency-Key
  • 422 – AML риск / IP не в белом списке
  • 429 – rate limit
  • 500 – внутренняя ошибка
  • 503 – сервис недоступен

Событие: TransactionSignedEvent

{
  "event_id": "evt-123",
  "event_type": "transaction.signed.v1",
  "occurred_at": "2023-10-27T10:25:00Z",
  "withdrawal_id": "wd-123e4567-e89b-12d3-a456-426614174000",
  "tx_hash": "0x123...abc",
  "signed_at": "...",
  "signer": "hsm-cluster-01",

Idempotency по полю event_id. Событие публикуется в Kafka.

ТерминОпределение
Compliance (комплаенс)Отдел соответствия требованиям 115-ФЗ и AML/CFT.
Legal (юридический отдел)Отдел, отвечающий за правовые вопросы и взаимодействие с регуляторами.
AML/CFTПротиводействие легализации доходов / финансированию терроризма.
Platform EngineeringКоманда, разрабатывающая и поддерживающая внутреннюю платформу (инфраструктура, базовые сервисы).
DevOpsРоль, отвечающая за автоматизацию развертывания приложений, мониторинг и пайплайны CI/CD.
HSM (Hardware Security Module)Аппаратный модуль безопасности. В проекте – on-premise кластер КриптоПро, сертифицированный ФСБ.
Tenant isolationЛогическая изоляция данных разных клиентов на уровне namespace и RBAC.
M-of-N (мультиподпись)Схема, требующая M подписей из N возможных для совершения транзакции.
RPS (Requests Per Second)Количество запросов в секунду, выдерживаемое системой.
SLA (Service Level Agreement)Соглашение об уровне обслуживания, например, доступность 99.95%.
RetentionСрок хранения данных (например, аудиторских журналов – 7 лет).
ThroughputПропускная способность системы (событий в секунду).
Latency p9999-й перцентиль задержки – значение, ниже которого находятся 99% запросов.
WORM (Write Once Read Many)Режим хранения, гарантирующий неизменность данных после записи.
